# Data-driven testing (15 Nov 2026, approved by the user; scope in `DATA_DRIVEN_SCOPE.md`)
Restore point before this work: git commit `07d1949`, tag `pilot2-before-data-driven` (the project was put under git first; secrets, `.env`, runner keys, node_modules and the UAT screenshots are not in it; `.gitattributes` keeps files byte-for-byte so the system prompts stay identical).
- **What it does:** a script no longer holds its test data as fixed text. Each step that has test data gets a key (`username`, `password`, `destination_url`...). The test case holds variations (DV-1 = the test data in the steps, locked; DV-2... = a name and a value per key; an empty cell uses DV-1). After the AI writes a script, a fixed rule replaces each value typed into a step by `DATA["key"]` and adds a data block at the top. When the script is **executed or downloaded**, the server writes the chosen variation's values (read from the test case at that moment) into the data block. So editing a value never needs a new script or an AI call.
- **Design choice you should know:** the runner is NOT changed. Instead of the runner reading a data file, the server fills in the data block before sending the script, so old runners (0.1/0.2/0.3) work and there is no new runner version. Consequence: values (also passwords) are still in the script text stored in the database and in the job, as before. The report shows the data used with secret-looking keys (password, token, secret, pin, api key) masked.
- **Code:** `app/engines/datadriven.py` (keys, values, the script rewrite; the AI prompts and `tsg.py` are untouched; the AI is shown the steps without keys), migration 0012 (`test_cases.data_sets`, `test_scripts.data_keys/data_gaps`, `test_runs.data_set`), `PUT /test-cases/{id}/data-sets`, `POST /test-scripts/{id}/make-data-driven` (older scripts, no AI), `execute` takes `data_sets` (one execution per variation; answer has `jobs`), `download?data_set=`, the run report and history carry the variation. Editing: a change of only the test data that the script reads keeps the script current (its stored data block is updated); any other edit still marks it "Out of date".
- **Screens:** test case page (Key column, variation picker in the Test Data header, "Add Data Variations" dialog like your mockup without the import buttons), script page ("Data-driven (n values)", "Make data-driven" for older scripts, a notice for steps whose value the AI wrote differently), Execute dialog (tick the variations; several = one list that follows all), report ("Data variation" and a "Data used" table).

# Test Batches (15 Nov 2026; scope in `TEST_BATCHES_SCOPE.md`, approved by the user with the additions listed there)
- **What it does:** a **Test Batches** tab in every project. A batch is an ordered list of up to 8 test scripts that run in ONE browser session, so a later script starts where an earlier one ended (already logged in, item already in the cart). Each script in a batch has its own data variation (DV-1 or one of its test case's variations; the same script may appear twice). The batch has a **When a script fails** setting: stop (default) or continue with the next script. Each script runs alone exactly as before; the person still provides the prerequisites for a single run.
- **How (runner unchanged):** the server joins the chosen scripts' text into one Playwright test (`app/engines/batch.py`). Every script keeps its own `ELEMENTS`, helpers and `DATA` block inside a function of its own; all share one `page`. The batch goes out as an ordinary `run_script` job with a `batch` block in the payload, so old runners work and there is no new runner version. Marker steps ("Step 0 TMX-START 2 TS-002", "... TMX-DONE ...", "... TMX-FAIL ...") between the scripts' own steps let the server cut the runner's flat step list into one result per script (`app/batch_service.py`). A screenshot of the page is attached after each script. Stop mode: the first failure ends the test. Continue mode: the failed script's error is recorded, the next script runs, and the test fails at the end. If Playwright wrote no report (cancel, kill) the markers are read from the console output instead.
- **Results:** per script passed / failed / aborted / not run (an earlier script failed and the batch stops, or the run was cancelled before it), plus an overall status. Each script that ran is also an ordinary execution (`TsRun`, "EX-nnn") of that script with its data variation and its own page screenshot; it shows in the script's own history (tagged "Batch") and its report says "Part of BR-nnn". A script that did not run gets no execution.
